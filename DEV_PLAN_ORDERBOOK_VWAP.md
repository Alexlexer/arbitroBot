## План внедрения глубины стакана и VWAP

Цель: бот считает спред **в моменте**, но уже не по одному лучшему тику, а **как маркет‑ордер на X USDT** по глубине стакана, с параметром `depth_usdt`, задаваемым из дашборда. Делать маленькими шагами, чтобы всегда можно было откатиться.

---

### Этап 1. Подготовка (без изменения логики)

- **1.1 Документация**
  - В `MATH_REVIEW.md`/`OPERATION.md` описать текущее поведение: спред считается по лучшему bid/ask, без учёта глубины.
  - Кратко зафиксировать целевое поведение: VWAP на `depth_usdt`.

- **1.2 Параметр `depth_usdt`**
  - В `AppConfig` завести поле `depth_usdt: Decimal` (дефолт, например, 50 USDT).
  - Протянуть его в дашборд (`BotConfig` и UI – инпут/ползунок “Depth (USDT)”). 
  - На этом этапе расчёт спреда **не трогать**, просто хранить и показывать параметр.

---

### Этап 2. VWAP‑утилита и расчёт “маркет‑спреда” (без влияния на торговлю)

- **2.1 Функция VWAP по глубине**
  - В агрегаторе реализовать функцию вида:
    - `fn vwap_for_volume(orderbook: &OrderBookDepth, side: Buy|Sell, target_usdt: Decimal) -> Option<(price, filled_usdt)>`.
  - Работает по уже имеющимся `bids/asks` (даже если там 1 уровень – тогда просто вернёт этот уровень).

- **2.2 Расчёт маркет‑спреда в `detect_sharps`**
  - Для найденной пары (long/short) считать:
    - `vwap_long = vwap_for_volume(long, Buy, depth_usdt)`
    - `vwap_short = vwap_for_volume(short, Sell, depth_usdt)`
  - Если по любой стороне `filled_usdt` заметно меньше `depth_usdt` (например `< 0.8 * depth_usdt`) – считать, что ликвидности недостаточно.

- **2.3 Только логирование**
  - Логировать для каждой возможности:
    - старый спред по лучшему тику,
    - новый маркет‑спред по VWAP,
    - `filled_usdt` по обеим сторонам.
  - Решение об арбитраже пока **не менять** – это чисто диагностический режим.

---

### Этап 3. Фича‑флаг для использования VWAP в логике

- **3.1 Флаг в конфиге**
  - В `AppConfig` добавить `use_vwap_pricing: bool` (по умолчанию `false`).

- **3.2 Условное использование VWAP**
  - В `detect_sharps`, если `use_vwap_pricing == true` и есть достаточная глубина:
    - использовать VWAP‑цены вместо `best_bid/best_ask` при расчёте спреда;
    - при недостаточной глубине просто не считать возможность.

- **3.3 Включение только для части бирж**
  - На первом этапе включать VWAP только если обе биржи, например, ∈ {Binance, Bybit, Bitget}, чтобы сузить зону риска.

---

### Этап 4. Перевод бирж на реальную глубину

Для каждой биржи отдельная мини‑задача. Делать **по одной**, с тестами:

- **4.x.1 Выбор API глубины**
  - Найти REST/WebSocket endpoint depth/orderbook для конкретной биржи (spot/futures).

- **4.x.2 Коннектор → `UnifiedTicker` с несколькими уровнями**
  - В соответствующем `*_launcher` вместо тикера собирать:
    - `bids: Vec<(price, size)>`,
    - `asks: Vec<(price, size)>`,
    - с ограничением по количеству уровней (`take(5)` или `take(10)`).

- **4.x.3 Проверка нагрузки и стабильности**
  - Проверить, что соединение держится, частота обновлений не душит CPU/сетку.
  - Убедиться, что `UnifiedTicker` не разваливает сериализацию/рассылку.

- **4.x.4 Включение VWAP для этой биржи**
  - Как только глубина стабильна, включать VWAP‑расчёт для пар, где участвует эта биржа (при `use_vwap_pricing = true`). 

Рекомендуемый порядок бирж: Binance → Bybit → Bitget → MEXC → Gate → Bitmart → Kraken → Ourbit/Okx.

---

### Этап 5. Глобальное включение VWAP

- Убедиться, что все нужные биржи отдают глубину и VWAP‑логика стабильно работает.
- Перевести `use_vwap_pricing` в `true` по умолчанию.
- Оставить старый код расчёта спреда как fallback для отладки (но не использовать в проде).

---

### Этап 6. UX и риск‑менеджмент

- В дашборде:
  - удобный контрол для `depth_usdt` (типовые значения 50 / 100 / 250 USDT);
  - визуальное обозначение пар, где ликвидность меньше заданной глубины.

- В риск‑менеджере:
  - увязать `target_volume_usdt()` с `depth_usdt`, чтобы бот не пытался торговать объём, который превышает глубину, по которой считается VWAP.
